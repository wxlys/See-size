# 目录扫描实际效果与成本验证（2026-10-21）

结论：当前受控规模下，成功扫描、目录增减、阈值告警、三种不完整原因与完整参考、硬失败保留原结果均按现有机制工作。真实文件→真实扫描程序→HTTPS 上传→线上 SQLite→公网浏览器展示链路已覆盖；未修改 Hub、主 Agent 或扫描算法。

原始报告：[disk-live-validation-20261021.json](evidence/disk-live-validation-20261021.json)。报告的 PASS 指脚本内断言通过，不代表已覆盖全部规模或下述产品体验不足已解决。

## 环境与方法

- wsrser：Ubuntu 20.04、Linux 5.4.0-216-generic、x86_64、2 个逻辑 CPU，MemTotal 1,917,532 KiB。
- 扫描程序由干净提交 6a19fdab15c22582bb1f78bc9df62db4e3904dc8 构建，Go 1.27.1、Linux amd64、CGO_ENABLED=0、-trimpath；SHA256 `9c39c47e4ecac542e0fc26fbc268133a414374ef3df71af1248208fbe8f28027`。
- 所有扫描 nice=10、ionice=idle。没有提权、清空缓存、重启服务、扫描整个根分区或修改业务目录。
- 使用真实受控文件；规模测试文件各 4096 字节，分布在 121 个目录节点中。增长演示使用稀疏文件，逻辑增长不等于实际新增物理写入。
- 使用 os.wait4 对每个扫描子进程独立计量 CPU 和峰值 RSS；耗时包括进程启动，上传案例还包括 HTTPS 上传。20ms 的退出轮询使极短任务的耗时只有近似参考意义。
- /proc/<pid>/io 为采样到的计数，不是退出时的精确最终值；另记录 wait4 文件系统输入/输出块数。没有控制冷缓存，也不是最大吞吐量测试。

## 成功场景与网页效果

专用设备 `disk-scan-success-20261021` 的 `success-files`：

1. 第一次完整扫描约 15 MiB 的逻辑大小，保存基线。
2. app-logs/app.log 从 8 MiB 调整到 136 MiB；cache/tmp.bin 从 4 MiB 调整到 1 MiB；删除 archive/old.bin 和 archive 目录。
3. 第二次完整扫描根目录约 138 MiB：app-logs +128 MiB，cache −3 MiB，archive −2 MiB（已移除），根目录净增长 +123 MiB。
4. 默认阈值 100 MiB，生成 app-logs 和根目录两个增长事件；父子增量重叠，不能将事件相加。
5. 真实浏览器通过同级大小/增长排序、占比、树展开、减少及删除目录、告警历史验证。

两次受控扫描相隔不足一秒，网页按秒格式化后可能显示相同起止秒；实际快照时间有更高精度，比较不是对同一条记录执行的。

## 失败和不完整场景

| 场景 | 触发方式 | 观察结果 |
| --- | --- | --- |
| 条目超限 | max-entries=3 | 正常返回部分快照，complete=false，reason=entry limit；网页中文原因正确 |
| 软超时 | rate=1、timeout=100ms | 正常返回部分快照，reason=time limit or cancellation；网页中文原因正确 |
| 权限不足 | 在专用测试目录创建并暂设为 000 的 restricted 子目录 | skipped>0，reason=unreadable or excluded entries；权限在扫描后恢复 |
| 连续不完整 | 完整基线后连续上传上述不完整结果 | 仍找到同设备/根目录/深度的完整基线；参考时间明确，不计算本次增量和增长告警 |
| 目录不存在 | 只指定专用测试路径中不存在的目录 | 退出码 1，stderr 为 lstat 错误，无新快照 |
| 上传凭据无效 | 仅使用专用无效测试凭据 | 退出码 1，HTTP 401，数据库未新增快照，页面保留此前结果 |

条目超限、软超时、权限不足均额外执行了一次真实上传，分别在公网浏览器截图；不是将模拟 API 数据塞进页面。最后保留权限不足场景供查看。成功返回部分快照时程序退出码为 0，需要检查 complete 字段而非只看退出码。

实际速率接近配置上限；这是主动节流的结果，不表示程序最大速度只有这些。CPU 百分比以单核为分母，不能直接当作两核整机占用，也不包含外部测试驱动和演示 Agent。

降低速率降低了本次扫描期间的平均 CPU，但这组结果的总 CPU 时间反而更高；不能承诺限速一定降低总 CPU 消耗。若以同一一万文件规模每半小时扫一次，0.719485 CPU 秒对应约 0.04% 单核的周期平均值，是按本次数据估算，不是持续挂测证明。

### 展示深度与保存成本

同一 1,000 文件目录：depth=3 与 depth=1 都扫描 1,121 条目，耗时 1.1468 与 1.1434 秒；目录节点从 121 降为 21，JSON 从 5,222 降为 922 字节。展示深度能减少保存和展示数据，但没有减少遍历范围。

以 5,343 字节/份、每半小时约一次、保留七天估算：约 336 份、1.71 MiB/设备。仅为快照正文，不含索引、事件、SQLite/WAL 页、TLS/HTTP 开销和七份整库备份，不能当成所有目录的固定大小。

本轮最终实际保存 10 份快照，JSON 正文共 4,109 字节：成功设备 2 份/821 字节、不完整设备 7 份/2,624 字节、varlog 设备 1 份/664 字节；另有两个增长事件。保留目录大小记录，没有复制被扫描文件内容。

/var/log/private、/var/log/letsencrypt、/var/log/unattended-upgrades 对 wsr 无目录读取权限，均只做元数据检查，没有提权。已扫描部分的 journal 约 392 MiB，但 /var/log 的完整总量无法据此确认。

这也证明了大文件总大小与扫描开销不是线性关系：备份文件较大但条目少，元数据扫描很快。实际部署优先选择允许读取的业务日志、上传或缓存目录；不同目录的规模、权限和缓存状况需要分别测量。

## 可见问题与未覆盖项

- 硬失败（路径不存在、上传拒绝）只在程序 stderr/退出码体现，Hub 没有接收新的失败状态；网页保留上次结果，不能误认为最近扫描也成功。后续如需完整状态闭环，应另行设计扫描任务结果上报。
- 不可读取子目录的节点可能显示 0 B；在部分扫描中，这不代表目录为空。未来应增加行级“未统计/不可读取”状态，不能用全局 incomplete 推断具体行都完整。
- 当前报告只覆盖最多一万普通文件和这两个真实目录，没有覆盖十万条目上限、百万文件、海量目录、网络文件系统、受控冷缓存、Agent 内置定时扫描长期运行。
- 快照上传限额、扫描硬限额、软时间预算仍维持原实现，本轮没有扩容或修改算法。
