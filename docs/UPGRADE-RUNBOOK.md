适用当前 wsrser：Ubuntu x86_64、普通用户 wsr、/home/wsr/seesize、systemd --user。旧 /opt/seesize-dev 安装脚本不用于新机，不能混用系统级和用户级服务。

## 只读检查

在本地 Windows PowerShell 7 的项目目录执行：

```powershell
Get-Content -Raw .\scripts\deployment-check.py | ssh wsrser "python3 - --root /home/wsr/seesize --mode installed"
```

脚本检查平台、专属目录、凭据权限（不读取或显示内容）、二进制 ELF 架构（不执行候选程序）、磁盘余量、用户服务管理器、Linger、自启状态和 healthz。不会安装软件、写服务器文件、重启服务或修改权限。blockers=0 才进入下一步；WARN 仍应解释，尤其 degraded 可能只是旧临时实例到期，但不能直接忽略所有失败单元。

新装准备目录检查使用 --mode install，要求程序、私有凭据、data/backups 已准备好，检查同名服务和端口未占用。它不是一键安装器，不验证凭据本身有效性、不验证二进制真实性、不保证所有运行库兼容，环境变化后安装前仍须复查。

## 升级流程（由维护者执行，不要直接批量复制运行）

1. 明确升级组件和协议/数据库兼容范围；确认当前健康、近期心跳和定时备份成功。记录旧程序哈希、服务配置及所有 drop-in。
2. 本地测试、构建 Linux amd64，计算哈希；上传新程序到独立 staging 名称，远端核对哈希及架构。不覆盖正在运行的程序。
3. 使用现有备份工具在线生成并验证独立升级前备份；新建唯一 pre-日期-版本目录，保留对应旧程序和配置。
4. 将新回退点登记 maintenance-artifacts.json，使用同格式 UTC created_at；保留最新三个。升级期间避免与每日维护冲突，临时暂停维护 timer，等待已运行维护退出后再操作，结束恢复原状态。涉及备份程序时同样协调备份 timer 和正在运行的备份任务。
5. 先 Hub 后 Agent：停目标服务、同文件系统替换候选程序、必要时 daemon-reload、启动。只更新需要变化的组件，不重启业务服务。
6. 轮询 healthz，验证登录、服务器清单、备份接口、实际心跳推进及错误日志。仅 healthz=200 不足以宣布升级成功。
7. 恢复原定时器状态，保存版本和验证结果，提交仓库记录。新临时产物登记到期规则，不遗留无限 staging 目录。

## 回退决策

- 程序兼容、无数据库语义变更：停止新程序，保留失败候选，恢复已验证的旧程序/配置并启动，重新完成步骤 6。
- 存在新字段/删除标记等语义变化：不可盲目换旧程序。例如旧 Hub 可能拒绝新 Agent 字段，旧版可能重新展示已删除身份；需回退匹配组件组合或修复前进。
- 数据库恢复：只能先恢复至新的独立路径验证；切换真实数据库需要明确确认数据损失时点，不能自动覆盖现库。旧备份可能复活当时的设备授权，应重新核验。
- 自动恢复未成功：停止反复重启，保留失败日志，向用户报告。不要执行 reset-failed 后无上限重试。

当前提供只读检查工具及操作规程，尚未实现全自动升级事务/断电回退器。常驻业务机不用于故意破坏式回退演练；该类实验放入独立虚拟机。
